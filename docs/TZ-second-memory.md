# ТЗ: вторая память проекта — знания и задачи через MCP

Версия 1 · 2026-09-26 · основа — сервис `preference-memory` (этот репозиторий)

## 1. Зачем

Агент тратит токены на то, что грузится в каждую сессию целиком, и на разведку кода.
Замеры на проекте `platform-self-hosted` (`claude -p` с пустым вопросом, 2026-09-26):

| Состояние | Стартовый контекст |
|---|---|
| Исходно (CLAUDE.md 431 строка, все плагины) | 64 213 токенов |
| После разреза CLAUDE.md на вложенные | 52 711 |
| Из них системный промпт, инструменты, глобальные правила | ~32 500 |
| Из них проектные файлы (CLAUDE.md, память, навыки проекта) | ~20 000 после разреза |

Цель: **проектная часть стартового контекста ≤ 5 000 токенов**, всё остальное агент запрашивает сам
через MCP — ровно то, что нужно задаче. Ожидаемый эффект: −20–30% токенов на задачу к состоянию
«карты пакетов + разрез CLAUDE.md», для работы группой агентов больше (стартовый контекст
повторяется в каждом субагенте).

## 2. Принципы

1. **Репозиторий — источник правды, память — индекс.** Правила, карты, спеки, документы, OpenAPI
   заливаются в память автоматически из `main`; руками в памяти не правятся. Памяти принадлежит
   только то, чего нет в репозитории: решения владельца, грабли окружения, ход задач.
2. **Минимальный стартер в CLAUDE.md проекта (~15 строк):** «первым вызови `memory.start`» и
   неснимаемые запреты (force-push, действия на проде, секреты, «спросить до кода»). Запреты не
   должны зависеть от того, вспомнит ли агент спросить память. Всё остальное — в памяти.
3. **Ответы адресные и короткие:** агент задаёт бюджет, по умолчанию 3 000 токенов; каждый кусок
   несёт источник `путь#якорь`, чтобы исходник читался точечно, а не целиком.
4. **Один сервис на все проекты**, изоляция по проекту (как проекты в `preference-memory`),
   ключ MCP на проект или общий `MCP_TOKEN` с полем проекта.
5. **Без памяти агент не слепнет:** стартер называет запасной путь — файлы репозитория.
6. **Секреты в память не попадают:** заливка маскирует ключи (`pk_live_…`, `pza_…`, `sk-…`, токены),
   `.env*` не читает.

## 3. Что хранится

| Вид (`kind`) | Что | Источник | Кто пишет |
|---|---|---|---|
| `rule` | разделы корневого и вложенных CLAUDE.md | репозиторий | заливка |
| `map` | карты пакетов `MAP.md` | репозиторий | заливка |
| `spec` | требования OpenSpec: specs, proposal, design | репозиторий | заливка |
| `task` | задачи change'ей (`tasks.md`) со статусом, MR, исполнителем | репозиторий + статусы | заливка, агент |
| `doc` | разделы `docs/*.md` | репозиторий | заливка |
| `api` | операции OpenAPI: метод, путь, право, поля кратко, коды отказов | `openapi/*.json` | заливка |
| `command` | карта команд: имя, назначение, владелец | карта команд | заливка |
| `decision` | решения владельца с датой и контекстом («MVP = волна 0 + этапы 1–3») | — | агент, веб |
| `gotcha` | грабли окружения («журнал bootstrap врёт порядком — ищи ✗») | — | агент, веб |
| `preference` | предпочтения (как сейчас) | — | как сейчас |

## 4. Модель данных (Qdrant, как в сервисе)

Коллекция `knowledge` (предпочтения остаются в своей). Точка = кусок ≤ ~600 токенов.
Payload: `project`, `kind`, `source` (`путь#якорь`), `title` (цепочка заголовков), `text`,
`commit`, `updated_at`, `hash` (кусок без изменений не переэмбеддится), `level` (для правил:
жёстко / по умолчанию), `status` (для задач), `links` (id связанных), `supersedes`.
Векторы: dense (текущая модель эмбеддингов) + полнотекстовый индекс payload по `text` и `title`
(точные имена классов и маршрутов модель эмбеддингов ищет плохо).

Резка: Markdown — по заголовкам с цепочкой родителей; OpenAPI — операция = кусок;
карта команд — команда = кусок; MAP.md — раздел пакета = кусок.

## 5. Заливка

- Манифест в репозитории проекта `.memory.yml`: ключ проекта, какие пути каким видом, исключения.
- Команда `memory-sync <repo>` (CLI в `apps/api` или отдельный скрипт): читает манифест, режет,
  считает хэши, эмбеддит **только изменённые** куски, удаляет исчезнувшие. Повтор без изменений —
  ноль вызовов модели.
- Запуск: job CI на `main` после слияния (основной путь) + вручную. Статусы задач агент
  меняет инструментом, они не перетираются заливкой (заливка трогает текст задачи, не статус).
- Миграция: заметки текущего `MEMORY.md` проекта → `gotcha`/`decision` одним прогоном.

## 6. Инструменты MCP (контракт)

| Инструмент | Что отдаёт |
|---|---|
| `start(task, project?, budget?)` | пакет на старт задачи: жёсткие правила по теме, решения владельца, куски карт и спек, открытые задачи, строка «что ещё можно спросить». По умолчанию 4 000 токенов |
| `search(query, kinds?, budget?)` | куски с источником и видом, гибридный поиск (смысл + точное совпадение имён) |
| `get(source)` | раздел целиком по `путь#якорь` |
| `map(package)` | карта пакета |
| `api(query)` | операции OpenAPI по методу и пути или словам |
| `tasks(change?, status?)` · `task_update(id, status, note, mr?)` | ход задач change'а |
| `remember(kind, text, links?)` | запись `decision` или `gotcha` с дедупликацией и поиском конфликтов (как `add_preference`) |
| `supersede(id, text)` | заменить устаревшее, старое хранится с пометкой |

Промпт MCP `start` — то же, что инструмент, для клиентов, которые берут промпты.
Каждый ответ: компактный Markdown, источник у каждого куска, в конце число токенов ответа.
`get_context_for_task` предпочтений остаётся и вызывается внутри `start` (одним вызовом —
и предпочтения, и знания).

## 7. Стартер CLAUDE.md проекта (образец)

```markdown
# CLAUDE.md

Знания проекта — во второй памяти (MCP `memory`). Первым вызовом каждой задачи —
`memory.start(<задача словами>)`; дальше `search`, `get`, `map`, `api` по мере надобности.
Решение владельца или найденные грабли — `memory.remember`.

Всегда, без памяти:
- ветка и worktree на задачу; force-push, reset --hard, удаление веток — только по прямой команде;
- действия на проде (выкат, запись в площадку) — только по прямой команде;
- секреты не печатать и никуда не копировать;
- сначала вопросы и план, код — после «да».

Память недоступна — правила в файлах: `CLAUDE.md` каталогов, `MAP.md` пакетов, `docs/`.
```

## 8. Веб

Раздел «Знания» рядом с предпочтениями: поиск, просмотр куска с источником, правка и замена
`decision`/`gotcha`, статус задач, статистика — какие запросы агенты делают и что не находят
(по ней дополняются документы).

## 9. Приёмка

1. Проектная часть стартового контекста ≤ 5 000 токенов (замер `claude -p`, как в разделе 1).
2. На 10 типовых задачах: нужное найдено первым запросом в ≥ 80% случаев; средний ответ ≤ 3 000 токенов.
3. Токены на задачу −20% к состоянию «карты + разрез CLAUDE.md» (три одинаковые задачи до и после).
4. Повторная заливка без изменений — 0 вызовов модели; удалённый раздел исчезает из памяти.
5. Сервис выключен — агент продолжает по файлам репозитория, стартер это называет.
6. Секреты из тестового набора (ключи, токены) в памяти не находятся поиском.

## 10. Этапы

1. **MVP (неделя):** виды `rule`, `map`, `doc`, `spec`; `memory-sync` + job CI; инструменты
   `start`, `search`, `get`, `map`; стартер CLAUDE.md на одном проекте (`platform-self-hosted`);
   замер по разделу 9.
2. **Решения и грабли:** `remember`, `supersede`, раздел в вебе, миграция `MEMORY.md`.
3. **Задачи и API:** виды `task`, `api`, `command`; `tasks`, `task_update`; статистика запросов.
4. **Качество поиска:** гибрид с полнотекстом, подсказка «что ещё спросить», отчёт «не нашли».

## 11. Риски

| Риск | Что делаем |
|---|---|
| Агент не спрашивает память | стартер требует `start` первым вызовом; запреты — в стартере |
| Память устарела | заливка только из `main`, `commit` в каждом куске, устаревшее помечается |
| Ответы раздуваются | бюджет на вызов, число токенов в конце ответа |
| Секрет попал в кусок | маскирование при заливке, `.env*` не читается, тест приёмки 6 |
| Смена модели эмбеддингов | переиндексация при старте — сервис уже умеет |
| Сервис недоступен | запасной путь — файлы репозитория |

## 12. Решения владельца (до начала)

1. **Где строить:** расширить `preference-memory` (рекомендую: api, mcp, web, Qdrant, бэкап уже есть)
   / отдельный сервис / на своей headless-платформе (коллекции + векторный поиск + коннектор).
2. **Заливка:** job CI на `main` (рекомендую) / локальный хук после коммита.
3. **Эмбеддинги:** как сейчас, OpenAI-совместимый провайдер (копейки за заливку) / локальная модель.
4. **Стартер:** только запреты и `start` (максимум экономии) / плюс короткий раздел навигации.

## 13. Доработка preference-memory — что именно менять

Сервис уже умеет главное: Qdrant с индексами и переиндексацией при смене модели (`qdrant/setup.ts`,
`reindex.ts`), обогащение и поиск дублей и конфликтов (`preferences/duplicates.ts`, `conflict.ts`),
определение контекста задачи моделью (`context/task.ts`), MCP на FastMCP (`apps/mcp`), веб, бэкап.
Не хватает: знаний проекта как отдельной сущности, заливки, отбора по бюджету и инструментов.

| Где | Что добавить | Переиспользует |
|---|---|---|
| `packages/core/src/knowledge/` (новый модуль) | `chunk.ts` — резка Markdown по заголовкам с цепочкой родителей, куски ≤ ~600 токенов; `openapi.ts` — операция = кусок; `sync.ts` — хэш куска, эмбеддинг только изменённых, удаление исчезнувших; `mask.ts` — маскирование секретов | клиент эмбеддингов `ai/provider.ts` |
| `packages/core/src/qdrant/` | коллекция `knowledge`: payload-индексы `project`, `kind`, `source`, `status`, `commit` + полнотекстовый индекс `text`, `title` (гибрид: смысл + точные имена классов и маршрутов) | `setup.ts`, `reindex.ts`, бэкап — коллекция добавляется в список |
| `packages/core/src/knowledge/pack.ts` | **отбор по бюджету**: куски по убыванию оценки, пока влезают в `budget` токенов (оценка — символы / 3 для кириллицы); остальное — строкой «что ещё можно спросить» (заголовки и источники) | — |
| `packages/core/src/context/task.ts` | `start()` = текущий `contextForTask` (предпочтения) + знания проекта тем же `classify()` (домены, проект), одним вызовом. Правила проекта в предпочтениях тоже получают `budget` — сейчас они отдаются целиком и с ростом раздуют ответ | `classify()`, `projectScope()` |
| `packages/core/src/knowledge/remember.ts` | `decision` и `gotcha`: запись с обогащением, поиском дублей и конфликтов, как `add_preference`; `supersede` — замена с историей | `preferences/duplicates.ts`, `conflict.ts`, `merge.ts` |
| `apps/mcp/src/tools/knowledge.ts` | инструменты `start`, `search`, `get`, `map`, `api`, `tasks`, `task_update`, `remember`, `supersede`; промпт `start`. `search` и `get` — без вызова модели (только эмбеддинг запроса), `start` — с `classify()`. В конце ответа — число токенов | `tools/common.ts` (формат ответа) |
| `apps/api/src/routes/knowledge.ts` | `POST /api/knowledge/sync` — CI присылает файлы и метаданные (проект, коммит), сервис режет и эмбеддит сам: логика резки в одном месте; `GET /api/knowledge/*` — для веба; журнал запросов агентов | `auth.ts`, `rateLimit.ts` |
| `scripts/memory-sync.ts` | CLI для CI проекта: читает `.memory.yml`, собирает файлы, шлёт в `/api/knowledge/sync`; ключ — из переменной окружения CI | — |
| `apps/web` | раздел «Знания»: поиск, кусок с источником, правка `decision`/`gotcha`, задачи, **статистика «что спрашивали и не нашли»** — по ней дополняются документы | компоненты раздела предпочтений |
| авторизация | MVP: общий `MCP_TOKEN` и поле `project` в каждом вызове (сервис личный); позже — токены на проект, чтобы CI одного проекта не писал в другой | `apps/mcp/src/auth.ts` |
| миграция | скрипт: заметки `~/.claude/projects/<проект>/memory/*.md` → `gotcha`/`decision` с источником | `remember.ts` |

Порядок работ совпадает с этапами раздела 10: сначала модуль `knowledge` + коллекция + `sync` + `start`/`search`/`get`/`map`
на одном проекте и замер; затем `remember` и веб; затем задачи, API и статистика.

Что сознательно не меняется: предпочтения остаются своей коллекцией и своими инструментами — у них другая жизнь
(пишет человек голосом или текстом), а знания проекта в основном заливаются из репозитория.
