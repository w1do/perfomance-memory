# Предпочтения пользователя — обязательный шаг перед любой работой

У пользователя есть MCP-сервер `preferences` («Сервис моих предпочтений»): что он любит, что не любит и жёсткие
ограничения к результату. Работа в этом проекте начинается с него — **не приступай к реализации, пока не получил
предпочтения и не сверил с ними план.**

## Шаг 1. Получить предпочтения (до кода, до плана, до правок файлов)

1. Вызови `get_context_for_task` сервера `preferences` (в Claude Code — `mcp__preferences__get_context_for_task`;
   если инструменты отложены, сначала загрузи их поиском инструментов по слову `preferences`).
   - `task` — 1–2 фразы: что делаем, язык/фреймворк, тип работы и **название проекта** из раздела «Проект» ниже.
     Пример: `"Семейный чат: добавить экран настроек уведомлений, React + TypeScript"`.
   - `applies_to` не передавай — он сужает выборку и может отрезать общие правила.
2. Правила проекта целиком: `get_project({ name: "<название проекта>" })`.
3. Если задача затрагивает отдельную область (тесты, git, UI, документация, тексты), дополнительно:
   `get_preferences({ query: "<область>" })`, при необходимости с `domain` (`programming`, `ai_assistants`,
   `project`, …) или `folder` (например, `"Программирование/Код"`).
4. Сервер недоступен (нет инструментов, 401, нет ответа) — **остановись**: скажи, что память предпочтений
   недоступна, и спроси, продолжать ли без неё. Не угадывай вкусы пользователя.

## Шаг 2. Сверить план с предпочтениями — до первой правки

До первого создания или изменения файла сопоставь задачу и план с полученными правилами и напиши пользователю
**видимым текстом** (не только в размышлениях) короткий блок «Сверка с предпочтениями» — даже для маленькой задачи и
даже если навык `preference-memory` советует ограничиться одной строкой. Сразу после блока продолжай реализацию в
том же ответе; останавливайся и спрашивай, только если в строке «Конфликты с задачей» что-то есть.

```
Сверка с предпочтениями
- Жёсткие ограничения: `file_lines <= 100 lines` → разобью на модули по ≤ 100 строк
- Не люблю: переусложнённые интеграции → без лишних сервисов и абстракций
- Люблю: подробная документация → README и doc-комментарии к каждой фиче
- Конфликты с задачей: нет  (или: «задача просит X, а правило запрещает X — как поступить?»)
```

- **Жёсткие ограничения** (блок «Жёсткие ограничения», поле `constraints`) — обязательные требования. Оператор
  уже записан как требование: `file_lines <= 100 lines` — каждый файл не длиннее 100 строк.
- **«Не люблю»** — избегай. **«Люблю»** — применяй. Сила 4–5 — строже, 1–2 — мягко.
- **Конфликт** правила с явной просьбой пользователя — спроси до начала работы. Если ответа нет, текущая просьба
  важнее сохранённого правила; отметь это в итоге.

## Шаг 3. Реализация и проверка перед сдачей

- Работай по плану из сверки.
- Перед тем как сказать «готово», проверь каждое жёсткое ограничение фактами (например, `wc -l` для
  `file_lines`) и исправь нарушения.
- Итоговый ответ обязательно содержит раздел **«Сверка с предпочтениями»**: каждое жёсткое ограничение и чем
  подтверждено его выполнение (например, «`file_lines <= 150`: rate.php — 37 строк»), какие «люблю» применены и
  каких «не люблю» избежал.

## Новые предпочтения

Если пользователь говорит о долговременном вкусе («не люблю…», «люблю, когда…», «запомни…», «всегда делай…»),
сохрани его: `add_preference({ text: "<его фраза почти дословно>", project: "<название проекта, если правило про
проект>" })` и сообщи результат (создано / обновлено / дубль и папку). Разовые указания к текущей задаче не
сохраняй.

## Безопасность

`MCP_TOKEN` и заголовок `Authorization` никогда не выводи в ответы, логи, коммиты и файлы проекта.
